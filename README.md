# МЦД и результаты фирм: отдельный исследовательский пайплайн

Код мастер-класса Школы городской экономики 2026. Исследует **переход уже действовавших
железнодорожных направлений на сервис Московских центральных диаметров**.

Основное сравнение: фирмы и гексы у станций D1–D4 против фирм и гексов у
станций направлений, которые в период панели остались обычной пригородной
железной дорогой. Исходы – выручка юридических лиц и число зарегистрированных
фирм в гексе по секциям ОКВЭД. Это исследование изменения *сервиса на уже
существующей железной дороге*, поэтому станции, которые не работали до 2014
года, исключаются из основного анализа.
Готовый реестр `input/rail_station_treatment_registry.csv` охватывает найденные
станции радиальных направлений и веток МЖД, Большого кольца, Ленинградского
направления ОЖД и оставшиеся станции вашего OSM-файла. Для предварительного
DiD-контроль включает Ярославское и Павелецкое направления, Казанское
(включая Шатуру), участок Рязанского восточнее D3 и пять отдельных
пригородных веток. Остальные станции на коридорах МЦД без подтверждённого
сервиса оставлены с неопределённым статусом.

## Хронология и treatment

| Линии | Запуск сервиса | Первый полный год `g` |
|---|---:|---:|
| D1 и D2 | 21.11.2019 | 2020 |
| D3 | 17.08.2023 | 2024 |
| D4 | 09.09.2023 | 2024 |

Даты сверены по [порталу Московского транспорта](https://transport.mos.ru/mcd/about),
[сообщению о запуске D3](https://transport.mos.ru/mostrans/all_news/116337)
и [сообщению Стройкомплекса Москвы](https://stroi.mos.ru/news/sobianin-dvizhieniie-po-mtsd-3-i-mtsd-4-zapustiat-v-2023-2024-ghodakh).
Машиночитаемая таблица – `input/mcd_line_launches.csv`.

Важно: календарных когорт всего **две**, хотя линий четыре. D1/D2 и D3/D4
запускались попарно. Даты реконструкции отдельных станций не используются как
даты treatment; если понадобится эффект новых платформ, это отдельный дизайн.

## Быстрый запуск

Клонируйте репозиторий и откройте **его корневую папку** в VS Code. Код
проверялся на Python 3.11; виртуальное окружение `.venv` намеренно не хранится
в Git и должно создаваться заново на каждом компьютере. Активация окружения
в PowerShell не требуется – используйте его `python.exe` напрямую.

Windows PowerShell, из корня репозитория:

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -m ipykernel install --user --name mcd_masterclass --display-name "Python 3.11 (MCD masterclass)"
```

Если `py -3.11` не находится, установите Python 3.11 и выберите его полный
путь для первой команды. Для macOS/Linux замените первую команду на
`python3.11 -m venv .venv`, а `.\.venv\Scripts\python.exe` – на
`.venv/bin/python`. В VS Code выберите для notebook kernel
`Python 3.11 (MCD masterclass)` (или интерпретатор из `.venv`). Требования
зафиксированы по версиям из рабочего окружения; не переносите саму `.venv`.

В `input/` уже лежат небольшой реестр станций, даты запуска и граница региона.
Большая база RFSD **не хранится в Git**: notebook автоматически скачивает
её из `irlspbru/RFSD` при первом запуске. При необходимости можно заранее
перенести partitions в `input/RFSD_hf/RFSD/year=2014/` …
`input/RFSD_hf/RFSD/year=2025/`. Дома АИС ФРТ необязательны
(`USE_HOUSES = False`); при включении положите их CSV в `input/houses.csv`.
Для побайтово одинаковых результатов переносите те же Parquet-партиции RFSD:
автоматическое скачивание использует текущую версию `main` на Hugging Face.

Сначала выполните `mcd_firms_pipeline.ipynb` целиком. Первый запуск может
быть долгим: он скачивает RFSD и строит кэши. Результаты появятся в `output/`,
которая также не хранится в Git. Затем запустите R **из корня репозитория**:

```r
install.packages(c("arrow", "data.table", "did", "ggplot2", "MatchIt"))
source("R/estimate_mcd_effects.R")
```

Для QGIS откройте полученные GeoPackage по [инструкции](qgis/WORKFLOW.md).
Сохранённый локальный проект QGIS не включён: его старые пути к данным не
переносимы. Параметры анализа (`MAP_YEAR`, `RADIUS_M`, `USE_HOUSES`) находятся
в начале notebook. Пересоздать чистый notebook из исходника можно командой
`.\.venv\Scripts\python.exe scripts/build_notebook.py` (это стирает
выполненные ячейки notebook).

## Порядок работы

1. Создайте Python 3.11 окружение по инструкции выше и выберите его kernel.

2. Откройте [реестр станций](input/rail_station_treatment_registry.csv) и
   [описание полей](input/README.md). Для обновления данных Wikidata запустите
   `python scripts/build_station_registry.py`; это не трогает большой RFSD и
   не перезаписывает ваш `input/rail_stations_verified.csv`.
3. Откройте `mcd_firms_pipeline.ipynb` из папки этого проекта. Для проверки
   выборки станций достаточно ячеек **0** и **2**, без загрузки RFSD в ячейке 1.
   Реестр целиком доступен как `all_stations`, а `stations` содержит только
   предварительные кандидаты для DiD. Ручная историческая сверка всё ещё нужна.
4. Запустите notebook целиком. Он скачает RFSD, если partitions нет в
   `input/RFSD_hf/`, и создаст панели.

   Исходный территориальный фильтр: `BBOX = (54.20, 35.10, 57.05, 40.30)` в
   порядке юг, запад, север, восток. Реестр станций дополнительно обрезается
   по полигонам Москвы и Московской области; первичная выборка **фирм** пока
   использует bbox, поэтому возле границы возможны наблюдения соседних
   областей. Перед финальной оценкой фирменную выборку также нужно обрезать
   по региональному полигону.
5. В R из этой папки выполните:

   ```r
   install.packages(c("arrow", "data.table", "did", "ggplot2", "MatchIt"))
   source("R/estimate_mcd_effects.R")
   ```

## Файлы на выходе

- `output/r_firm_year.parquet` – фирма × год, cohort по исходному catchment;
- `output/r_hex_year.parquet` – гекс × год, нули заполнены, секции ОКВЭД
  разделены как `firms_A`…`firms_U` и `log1p_firms_A`…`log1p_firms_U`;
- `output/qgis_rail_stations_all.gpkg` – весь реестр для QGIS, создаётся уже
  ячейкой 2 без обработки фирм;
- `output/qgis_cells.gpkg` и `output/qgis_rail_stations.gpkg` – гексы и
  предварительная DiD-выборка станций;
- `output/qgis_firms_four_groups_{MAP_YEAR}.gpkg` – все фирмы за выбранный год
  внутри Москвы и области для карты QGIS. Поле `firm_group`: `treatment`,
  `control`, `neither`, `overlap_excluded`; `near_both=1` отмечает фирмы рядом
  одновременно с МЦД и контрольным направлением;
- `output/mcd_staggered_att.csv` – средние ATT по отраслям;
- `output/mcd_matched_heterogeneity.csv` – простая оценка изменений после
  matching для выбранной когорты;
- `output/mcd_matched_hex.csv` и `output/mcd_matched_hex.png` – matched DiD
  на гексах: число фирм всего и по выбранным секциям ОКВЭД, а также общая
  выручка и активы всех отраслей. Денежные исходы – `asinh(сумма / 1e6)`;
  пустой гекс считается нулём, а отсутствие финансовой отчётности при наличии
  фирм остаётся пропуском;
- PNG event study и гетерогенности.

Код notebook хранится также в `pipeline_source.py`. Если вы редактируете этот
источник, пересоздайте notebook командой
`python scripts/build_notebook.py`. Выполненные ячейки и промежуточные данные
в Git не сохраняются.

## Как устроен дизайн

1. Берём только станции, работавшие как обычные железнодорожные остановки до
   2014 года. Сохраняем их координату, принадлежность к направлению и ссылку
   на источник.
2. В радиусе 800 м строим одинаковые гексы. Гексы с доступом к нескольким
   направлениям помечаем `ambiguous=1` и исключаем из основной оценки.
3. Привязываем ежегодные юридические адреса фирм к гексам. Фирменный treatment
   фиксируется по первой наблюдаемой локации; для консервативной оценки
   оставляем фирмы без перемещений.
4. Для гексов считаем фирменные counts по секциям ОКВЭД, для фирм –
   `asinh(revenue / 1e6)` и другие финансовые показатели.
5. В R используем `did::att_gt` с обычными железнодорожными направлениями
   (`g=0`) как `nevertreated` control. Дополнительно сравниваем matched
   изменения для когорты 2020 или 2024 (`MATCH_G`). Для мэтчинга контрольная
   фирма не обязана наблюдаться с 2014 года: достаточно данных в заданных
   `MATCH_PRE` и `MATCH_POST`. Отбор и 1:1 мэтчинг проводятся отдельно для
   каждого исхода; постстратификация выключена.
   Аналогичный 1:1 мэтчинг гексов использует расстояние до станции и средние
   pre-treatment значения исхода и общего числа фирм.

## Методические ограничения

- Запуск МЦД включал тарифную интеграцию, новый график, реконструкцию,
  подвижной состав и пересадки. Оценка относится к пакету изменений.
- Направления для МЦД выбраны не случайно. Обычные железные дороги могут иметь
  иные тренды; нужны предтренды, контроль других транспортных проектов и
  проверки на разных радиусах.
- Treatment фактически назначен только четырём коридорам. Даже при большом
  числе гексов и фирм число независимых treated-кластеров мало: интервалы и
  p-values следует считать ориентировочными, без сильных причинных выводов.
- Координаты фирм – юридические адреса; особенно осторожно следует читать
  результаты для сетевых компаний. Переезды и закрытия меняют состав
  фирменной панели. Для extensive margin предпочтителен уровень гекса.
- Текущая геометрия железнодорожных платформ из OSM может не совпадать с
  положением до запуска МЦД. Проверяйте реконструированные и перенесённые
  платформы по историческим источникам.
- Matching улучшает баланс по наблюдаемым данным, но не решает проблему
  выбора направлений и не создаёт независимые линии treatment.
- Для каждого исхода CSV показывает `treated_with_outcome` и
  `treated_retained_share`: так видно, сколько фирм действительно вошло в
  мэтчинг. SE в блоке мэтчинга – ориентировочная дисперсия парных разностей,
  не поправка на малое число железнодорожных коридоров.

## Направления для дальнейшего исследования

- Добавить исторические координаты платформ и дату реконструкции каждой.
- Сравнить 500, 800 и 1200 м или расстояние по пешеходной сети.
- Исключить catchment нового метро, МЦК и БКЛ в годы их открытия.
- Сделать placebo дату до запуска МЦД и отдельные результаты для D1/D2,
  D3/D4 и разных секций ОКВЭД.
